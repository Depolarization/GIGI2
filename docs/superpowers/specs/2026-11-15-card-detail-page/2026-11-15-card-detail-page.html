01决策摘要

一句话：容器从 ModalBottomSheet 换成全屏 Route；顶部只留一组切换语义；所有格式选择收进下载对话框；全站字号回到 Material 3 类型标尺。

容器
全屏详情页

Route cardwiki/detail/{content_id}，复用壳层 TopAppBar（固定标题「卡牌详情」+ 返回）。进入默认「卡面」Tab。

切换语义
只保留 TabRow

动效
与图鉴页同款指示器

复用工程内 RankRoute / CardStatsRoute / CardWikiRoute 的 SecondaryIndicator + Pager 连续偏移：拖动跟手，点击 Tab 走 animateScrollToPage。

排版
M3 类型标尺

正文 11.5 → 14sp，技能名 13 → 14sp，标签 9.5 → 12sp，图标 40 → 56dp。全部落在 M3 token 上。

数据
JSON 归一化

冒号不是 HTML 解析问题：官方 attr 的 key/value 冒号位置不统一。新增 value 规范化，结构字段 100% 走 JSON。

下载

03根因诊断

3.1 为什么「拥挤」不是间距问题，而是层级问题

当前卡面 Tab 从屏幕顶到图片之间有四层：标题行 → TabRow → 格式分段 → 下载按钮。其中 TabRow 与分段按钮都是「互斥切换」控件，用户要先理解「我在切内容」还是「我在切格式」，这是语义冲突，不是 padding 能修的。

层职责改造后归属
标题 + 关闭标识对象 / 退出壳层 TopAppBar（标题 + 返回）
TabRow切内容（卡面 / 技能）页面内唯一切换控件
SegmentedButton切下载格式删除 移入下载对话框
下载按钮动作卡面 Tab 底部唯一动作按钮

3.2 冒号的真正来源（官方 JSON 实测）

拉取两张魔物牌的真实 entry_page，基础信息 attr 的冒号位置正好相反：

// entry_page_id = 502960 炽热骗骗花（现状显示正常）
"attr":[
  {"key":"元素：",  "value":["火元素"]},
  {"key":"武器：",  "value":["其他武器"]},
  {"key":"阵营：",  "value":["魔物"]},
  {"key":"充能：",  "value":["3点"]},
  {"key":"获取方式：","value":["无"]}
]

// entry_page_id = 502488 浊水幻灵（现状显示 "：其他武器" "：魔物"）
"attr":[
  {"key":"元素",  "value":["：水元素"]},
  {"key":"武器",  "value":["：其他武器"]},
  {"key":"阵营",  "value":["：魔物"]},
  {"key":"充能",  "value":["：2点"]},
  {"key":"获取方式","value":["：无"]}
]

现有代码只对 key 做了 normalizeKey()（去尾冒号），value 原样上屏，于是第二类卡把冒号带进了芯片。这与 HTML 解析无关。

3.3 指示器为什么生硬

当前实现直接读 tabPositions[selected] 并写进 Modifier.offset { IntOffset(...) }：布局阶段瞬间生效，没有动画宿主。M3 原生 tabIndicatorOffset 内部对 left 与 width 各跑一条 animateDpAsState，两者同步插值，才会出现「整条下划线平移并伸缩」的原生手感。

3.4 字号为什么「小到看不清」

现状字号 9.5 / 10 / 10.5 / 11.5 / 12.5 / 13 / 14.5sp。Material 3 类型标尺的最小正文 token 是 labelSmall 11/16、bodySmall 12/16。也就是说当前大量文本（芯片 9.5、获取方式 9.5、注释 10.5、数量 9.5）落在标尺之外，只能靠加粗补偿，反而更糊。

08数据与解析：更纯净的获取方式

8.1 官方接口到底给了什么

以「浊水幻灵」entry_page 为例，页面只有 3 个模块：基础信息、卡牌技能、召唤物。技能对象的字段是：

tab_name      技能名（纯 JSON）
skill_type    普通攻击 / 元素战技 / 元素爆发 / 被动技能（纯 JSON）
icon          图标直链（纯 JSON）
life, energy  费用素材（纯 JSON）
desc.key      描述标签，如「技能效果」（纯 JSON）
desc.value[]  HTML 片段 ← 唯一非结构化字段
tab_id        内部 id（未使用）
结论：结构字段已经 100% 来自 JSON，只有「描述正文」在官方数据里只有 HTML 一种形态。 要彻底去掉 HTML，只能换非官方数据源（第三方卡牌库），会引入更新滞后与授权风险，不推荐。 正确做法是把 HTML 依赖压缩到「一段散文」这一件事，其余一律 JSON。

8.2 冒号修复：只改数据规范化

不改 HTML 解析器，只在 domain/CardDetailParser.kt 增加纯函数，并在所有读 attr 的出口（芯片、徽章、获取方式、元素判定）统一套用：

/** attr 的 key / value 冒号位置官方并不统一，读取时必须双向归一 */
fun normalizeAttrValue(raw: String?): String = raw
    ?.trim()
    ?.trimStart('：', ':')     // 「：水元素」→「水元素」
    ?.trimEnd('：', ':')       // 「水元素：」→「水元素」
    ?.trim()
    ?.replace(Regex("[\\t\\u00A0 ]+"), " ")
    .orEmpty()

// 获取方式统一重建，避免 key 冒号 + value 冒号叠加出「：：无」
footText = normalizeKey(key) + "：" + values.joinToString("，")
输入现状上屏规范化后
key「元素：」value「火元素」火元素火元素
key「元素」value「：水元素」：水元素水元素
key「武器：」value「其他武器」其他武器其他武器
key「武器」value「：其他武器」：其他武器其他武器
key「获取方式」value「：无」获取方式：无（侥幸正确）获取方式：无（确定正确）

8.3 HTML 解析的边界（保留但收紧）

  • 白名单标签：br / p / div / li / h1-h6 / tr 只用于断行；strong / u / span[style] 丢弃样式只留文字；span[data-type="详情"] 抽为注释。
  • 引号感知：魔物牌的 data-name 内含未转义的 <p style="…">，开标签扫描必须跳过引号内的 >（已修，11 例单测）。
  • 不做语义猜测：不从 HTML 里推断技能类型、费用、标签、数量 —— 这些全部来自 JSON。
  • 注释默认展开后，data-name 仍是唯一来源；不引入第三方富文本库（体积/维护成本 > 收益）。

8.4 数据契约的两个坑（写成注释 + 测试）

  • 召唤物 模块的 component_id 也叫 card_skill，且 list 结构与技能完全同形。解析必须按 模块名「卡牌技能」取，不能按 component_id（现状正确，补测试钉死）。
  • 同一角色可能有多个「卡牌技能」模块（变体卡），只取第一个（现状正确）。

8.5 缓存从 ViewModel 上移

弹层是应用级单例，页面则随回退栈销毁。若继续把 LRU 放在页面 ViewModel 里，每次返回再进都会重新请求。方案：把解析结果缓存上移到 AppContainer：

class CardDetailCache(private val max: Int = 200) {
    // key = "<lang>:<entryId>"；accessOrder LRU；纯 JVM 可测
    fun get(key: String): CardDetail?
    fun put(key: String, detail: CardDetail)
}

页面 ViewModel 只负责：请求、解析、状态机、下载。默认 Tab 在每次进入时复位为「卡面」（用户明确要求）。
