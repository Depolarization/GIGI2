GIGI · Android · 改造报告

UID 查询历史快照 · 对局本地全量归档

两个需求共用一条数据主线：把「一次性网络结果」变成「设备上的可复用资产」。
查询历史是 5 条以内的账号级快照；对局归档是无上限的账号级流水，二者都要求「只在正确的写入点写入」。

2026-11-16 范围：查询弹窗 / 首页对局 / 数据层持久化 不改 API 协议 不引入 Room
摘要 现状取证 关键决策 ① 查询历史 ② 对局归档 首页渲染改造 红线与隐私 测试与验收 实施顺序

00结论摘要

两件事都不需要改接口，也不需要新增依赖；工作量集中在一个新的「账号级本地存储层」和首页列表容器的重构上。

需求 ①
查询历史 = 账号级 5 条快照

输入框下方直接跟列表，不加大标题、不加清除按钮、不加时间。头像 40dp，昵称 titleSmall，UID bodySmall，行高 56dp。

需求 ②
对局 = 本地 JSON 归档 + 合并去重

远端只给最近 10 局，本地无上限；每次刷新按 trans_no 去重入库，首页统一渲染合并结果。远端失败但本地有数据时不报错。

必须一起改
首页列表容器：Column → LazyColumn

现在是「整页 verticalScroll + 直接渲染最多 10 条」。全量后必须换成单一 LazyColumn，否则几百条会同时组合、内存与滑动都不可接受。

一句话口径：查询历史只记「用户在弹窗里主动查的人」；对局归档只记「官方窗口里出现过的比赛」，二者都按 账号 UID + 服务器 隔离，不跨账号串数据。

1.2 对局：只有网络结果，没有本地账本

// HomeViewModel.kt L138-L159（现状）
val next = try {
    Async.Content(
        container.repository.fetchGameRecordsCached(uid, server, force).gameRecords.orEmpty(),
    )
} catch (e: Exception) { Async.Error(apiErrorText(e)) }
  • 数据源只有 get_game_records，服务端窗口约 10 局；超出窗口的历史**永久丢失**。
  • 只有 45 秒的进程内缓存（cachedPrivate），进程重启即清零；断网时首页只剩错误态。
  • HomeRoute 用 Column + verticalScroll 直接 forEach 渲染，代码里已有注释「服务端最多返回 10 条」。 全量后这个前提不成立，必须换容器（见 §05）。
  • GameRecord.transNo 是服务端对局流水号，可直接作为去重主键；缺失时用「时间 + 对手 + 胜负」兜底。
必须诚实说明的上限：归档只在「打开首页 / 下拉刷新 / 回前台」时补齐。 若两次同步之间打了超过 10 局，中间超出官方窗口的对局拿不到——这是数据源决定的，不是实现取舍。 本报告仍会把「回前台静默同步」纳入，把窗口从「每次开 App」压缩到「每次回 App」。

02关键决策

议题选择理由 / 被否方案
查询历史归属维度 账号级：sessionUid + serverId，上限 5 条，按 UID 去重并置顶 UID 是服务器范围的，跨账号/跨服混排会点出「查无此玩家」。全设备共用一份会导致换号后历史错乱。
历史写入时机 手动提交（或点历史项）→ 详情查询成功且拿到昵称后写入 提交即写会产生「查无此玩家 / 无权限」的垃圾条目，且拿不到头像昵称。
否：查询失败也记录 UID（列表头像与昵称会长期为空）。
对局存储介质 账号级 JSON 文件 + 原子写（filesDir 私有目录） 不引 Room（当前工程无 KSP，仅加依赖与注解处理不值当）；条目是追加型快照，不需要查询语言。
否：塞进 DataStore Preferences 存一个大字符串（每次写整份、体积增大后不合适）。
去重主键 trans_no；为空时 timestamp|nickname|result trans_no 是服务端流水号；兜底键仅在异常数据上生效，冲突概率极低（同秒 + 同对手 + 同胜负）。
远端失败时的对局展示 本地非空 → 展示本地，不报错；本地为空 → 维持现有整屏错误 归档的意义就是断网可读；此时把已有历史藏到错误页后面，等于白存。
对局上限 不设上限 用户明确要求「本地对局数无限制」。1 条约 200 B，1 万局约 2 MB，仍在可控范围。
本轮是否引入 Room 否 两个存储都是「整份小数据 / 追加型快照」，文件 + 内存镜像足够；Room 会带来构建复杂度与迁移成本。

03① UID 查询历史快照

3.1 数据模型

@Serializable
data class QuerySnapshot(
    val uid: String,          // 9 位，去重主键
    val nickname: String?,    // 查询成功后回填
    val avatarUrl: String?,   // 查询成功后回填
    val serverId: String,     // 写入时所在服务器
    val queriedAt: Long,      // 最近一次查询时间（用于排序兜底，不上屏）
)

列表顺序 = 文件内顺序 = 最近查询在前。点击历史项视作一次查询：重新请求并把该条移到第 1 位。

3.2 存储

  • 复用现有 datastore-preferences（不加依赖），文件 player_query_history，键 gigi:query-history:<server>:<accountUid>，值是上述列表的 JSON。
  • 损坏/解析失败 → 视为空列表（与 WikiDiskCache 的 ReplaceFileCorruptionHandler 同一哲学），不向页面抛错。
  • 写入 = 读当前列表 → 去除同 uid → 头插 → take(5) → 整体写回（单条最大 5 条，成本可忽略）。
  • 对外暴露 Flow<List<QuerySnapshot>>，由 combine(sessionUid, currentServer) 驱动；会话为空时发空列表。

3.3 写入链路

3.5 边界与结论

  • 同一 UID 重复查询：不留重复项，直接置顶（快照不是日志）。
  • 超过 5 条：淘汰最久未查询的一条。
  • 换账号 / 换服：各自 5 条，互不可见（键空间已隔离）。
  • 登出：数据保留在设备私有目录（同一账号再登录仍可见）；本轮不提供清除入口（不属于「列表外」）。
  • 点击历史后：弹窗立即关闭（与手输一致），详情以新查询结果为准。

04② 对局本地全量归档

4.1 架构

HomeViewModel
   │  loadRecords()
   ▼
GigiRepository.syncGameRecords(uid, server, force)
   │
   ├─ ① 读本地：MatchArchiveStore.load(uid, server)      → 立即可渲染
   ├─ ② 拉远端：GET get_game_records（窗口内最新 N 局）
   ├─ ③ 合并：remote ∪ local，按 key 去重，remote 覆盖同 key
   ├─ ④ 排序：timestamp 倒序（同秒按 archivedAt 倒序）
   └─ ⑤ 落盘：仅在有新增/变化时原子写 + 更新 lastSyncAt
   ▼
List<GameRecord>（全量） → 首页 LazyColumn

4.2 存储格式

filesDir/match_archive/<serverId>_<accountUid>.json
{
  "version": 1,
  "serverId": "cn_gf01",
  "uid": "350347778",
  "lastSyncAt": 1794791686000,
  "records": [ { "nickname": "...", "avatar_url": "...", "result": "Win",

  • 写入 = 写 *.json.tmp → rename 覆盖，避免中途被杀导致半截文件。
  • 读取失败（文件损坏 / 版本不认识）→ 当作空库并记录一次日志，下次同步重建，不影响页面。
  • 内存中保留一份 MutableStateFlow<List<GameRecord>>，按账号缓存，避免每次进首页都读盘。

4.3 合并与去重

// domain/MatchMerge.kt —— 纯函数，JVM 直测
fun matchKey(r: GameRecord): String =
    r.transNo?.takeIf { it.isNotBlank() }
        ?: "t:${r.timestamp}|n:${r.nickname}|r:${r.result}"

fun mergeMatches(
    local: List<GameRecord>,
    remote: List<GameRecord>,
    now: Long,
): List<GameRecord> {
    val byKey = LinkedHashMap<String, GameRecord>()
    local.forEach { byKey[matchKey(it)] = it }       // 旧值先放
    remote.forEach { byKey[matchKey(it)] = it }      // 同 key 用远端覆盖（积分等字段可能修正）
    return byKey.values.sortedWith(
        compareByDescending<GameRecord> { it.timestamp?.toLongOrNull() ?: 0L }
            .thenByDescending { archivedAt[it] ?: 0L }
    )
}
  • 无上限：不截断、不采样。
  • 稳定排序：时间相同（同一秒内的两局）时按入库先后倒序，保证多次刷新顺序不跳。
  • 只在「合并结果 != 内存列表」时写盘；下拉刷新但无新对局时零写盘。

4.4 失败与降级矩阵

远端本地首页表现写盘
成功空远端窗口内的对局（首次入库）是
成功非空合并后的全量，新的在上有新条目时
失败（网络/retcode）非空展示本地全量，不显示错误否
失败空保持现有整屏错误 + 重试否
成功但返回空数组非空展示本地全量（不清库）否
不要做的事：远端返回空就用空覆盖本地。官方窗口偶尔会短暂返回空/少条， 用「覆盖」会让本地历史凭空消失；合并语义天然规避这个问题。

05首页渲染改造（全量的前提）

5.1 为什么必须改

现状是 Column + verticalScroll，记录用 forEach 直接组合；注释里明确写着 「服务端最多返回 10 条」。全量后：

  • 1000 条 = 1000 个 Composable 同时存在，首次组合与内存都不可接受；
  • 整页 verticalScroll 与 PullToRefreshBox 的组合在超长内容下也没有回收机制。

5.3 ViewModel 状态流

private fun loadRecords(uid, server, force) {
    val gen = ++recordsGeneration
    val local = repository.localMatches(uid, server)       // 同步读内存镜像
    if (local.isNotEmpty()) {
        _uiState.update { it.copy(records = Async.Content(local)) }   // 不进 Loading
    } else if (!silent) {
        _uiState.update { it.copy(records = Async.Loading) }
    }
    viewModelScope.launch {
        val next = try {
            Async.Content(repository.syncGameRecords(uid, server, force))
        } catch (e: Exception) {
            if (local.isNotEmpty()) Async.Content(local)
            else Async.Error(apiErrorText(e))
        }
        if (gen == recordsGeneration) _uiState.update { it.copy(records = next) }
    }
}
  • 首载 pendingLoads / refreshing 语义保持不变，下拉圈仍由「请求清零 + 两块落定」控制。
  • 回前台同步：fun syncRecordsOnResume()，同一条链路但不动 profile，60 秒去抖。

06红线与隐私

本需求会改写一条既有设计红线。 WikiDiskCache.kt 开头写明：「公开静态数据才允许落盘——私有数据（主页/对局/排行/卡牌统计/凭据）一律只走内存层」。 本轮按你的明确要求，把「对局」与「查询历史」纳入落盘白名单，其余私有数据仍然只走内存。
  • 存储位置：filesDir（应用私有，其他应用不可读），卸载即清除。
  • 键包含账号与服务器，不跨账号混排；登出不清盘（同一账号回来仍可见）。
  • 不写日志、不上传、不导出；对局库仅在首页与详情页内使用。
  • 查询历史只存「UID + 公开昵称/头像」，不存任何凭据。
  • 凭据（Cookie / DS）继续只走 CredentialStore，本次改动不触碰。

  6. 断网点刷新 → 首页仍显示上一次的全量列表，无错误页；再联网刷新 → 新对局并入顶部。
  7. 200% 字体 / 浅色 / 夜间检查弹窗与首页列表。
  8. 滚到列表底部无卡顿、无重复 key 崩溃（IllegalArgumentException: Key was already used）。
