# 任务执行范式：必分解、必委派

## 0. 铁律（2026-09-22 用户口述确立，**优先级最高，覆盖此前所有旧做法**）

| #  | 铁律                           | 判据 / 违反后果                                                  |
| :- | :--------------------------- | :--------------------------------------------------------- |
| 1  | **主代理不具体执行任何任务**             | 主代理只做 5 件事：统筹、规划、分解、划定独占文件、验收与汇总。改代码/改文件/跑命令**一概不由主代理亲自做** |
| 2  | **任何"要动手"的任务先分解再派子代理**       | 不存在"任务太小就自己顺手做掉"这一档。判据：只要会产生文件改动或需要跑命令，就必须派                |
| 3  | **第 0 档是唯一例外**               | 纯解释/查证/建议——不派子代理、不改文件、不跑命令，主代理直接回答                         |
| 4  | **验收不采信子代理自述**               | 必须独立复算：`git show` 逐行审 diff、复算数字、自己重跑检查命令                   |
| 5  | **子代理报告必须简短（≤200 字）**        | 结论 + commit hash + 证据路径；目的是尽量减少主代理注意力分散。过程细节写探针，不塞汇报       |
| 6  | **可控范围内尽可能多用子代理**            | 能并行就并行（并发上限 **3–4**）；主代理的注意力留给规划与验收                        |
| 7  | **开工前先定完成标准，完成后立刻停**         | 完成标准 = "全部满足才算完成"，含真机证据要求；达到即停并完整汇报                        |
| 8  | **不用 WorkBuddy 内置 subagent** | 实测 429 用量超限、零产出（见 §3）                                      |

## 1. 主代理的职责边界

**做：**

- 先自己调查到能写出"具体执行方向"（见 §5.2），再派单；
- 判定任务规模与档位（§2），切分文件归属（§5.3）；
- 派发、守望子代理存活，必要时补派接手（命令细节见 skill `subagent-cli-ops`）；
- 独立验收（§6）与统一修复的调度；
- 向用户汇总最终报告。

**不做：**

- 不亲自改代码 / 改文件 / 跑命令（第 0 档除外）；
- 不把"理解"外包：派单里要写清"改什么、怎么改"，不要写"基于你的发现去修"；
- 不在验收期间派修复代理改同一批文件（会让验收结果作废）；
- 不为"有活干"而给任务找额外拓展（§9）。

## 2. 分档与选型（先判档，再选策略）

| 档               | 判据                          | 做法                                               | 并发       |
| :-------------- | :-------------------------- | :----------------------------------------------- | :------- |
| **0 档** 问答      | 不执行任务：纯解释、查证、建议             | 主代理直接回答。**不派子代理、不改文件、不跑命令**                      | —        |
| **1 档** 单文件/单改动 | 改动落在一个文件内（或一个逻辑改动）          | 派 **1 个** CLI 子代理（方案②）                           | 1        |
| **2 档** 多文件/多模块 | 改动跨多个文件，可**按文件归属独占**切开      | 切 **2–4 块**并行，各派 1 个 CLI 子代理（方案②）；共享文件串行或指定单一负责人 | 2–4      |
| **3 档** 大工程/多期  | 如"某页面+业务逻辑完整重构""读大量文件写文档系统" | **分层**（方案③）：主 → 直接子代理 → 子代理再派子代理；启用协调网络（§7）      | 直接子代理 ≤5 |

- 判据含糊时**取小不取大**：先按小档派，不够再补派（补派成本远低于返工）。
- **不要一律拆细**：过度拆分会让每个子代理都完整读一遍规范，纯浪费通信与额度。
- 方案②的子代理**不得再派子代理**；方案③允许，但要在派单里写明。
- 派单内容只需：任务内容 + 简单指导（要求其自行规划、分解、必要时再委派，并在速度/成本/质量间取平衡）。**主代理不必替子代理负责其内部调度。**

### 分档实例

| 任务                       | 档   | 切法                          | 派几个      |
| :----------------------- | :-- | :-------------------------- | :------- |
| "这个颜色不对，改成主题色"           | 1   | 单文件单改动                      | 1        |
| "解释一下这个函数的执行顺序"          | 0   | 不派、直接答                      | 0        |
| 4 个对话框边距逐个修正             | 2   | 按文件归属切成 2–4 组（同文件必合并给同一个代理） | 2–4      |
| "修一个 bug 但需先读 5 个文件"     | 1–2 | 先派 1 个只读调研代理定位 → 再派 1 个实现代理 | 1 → 1    |
| "AI 模型管理页面 + 业务逻辑完整重构"   | 3   | 分层：先架构调研 → 页面线/逻辑线，各线再拆     | 直接子代理 ≤5 |
| "打包模块完整重构"、"读大量文件编写文档系统" | 3   | 分层 + 协调文件                   | 直接子代理 ≤5 |

### 完成标准的写法（任务区块里必须先写好）

- 形如：「① 静态检查三条全 0；② 真机截图证明目标页面无错位；③ 提交署名正确」——**全部满足才算完成**。
- 每条都要有**客观判据或检查命令**，不要写"看起来正常"。
- 标准无法满足但已到能力边界 → 写 `blocked` + 原因 + 保留项，**禁止伪造证据、禁止改换目标**。

### 子代理报告模板（≤200 字，硬上限）

```
<任务ID> done。改动：<文件清单，一行>。验证：<检查命令> 全 0 / 截图 <路径>。
commit <hash>。问题：<一行，或"无">。
```

## 3. 已废止的两条旧做法（**已废止，不要再做**）

| 旧做法                          | 状态        | 原因（保留一句）                                                      |
| :--------------------------- | :-------- | :------------------------------------------------------------ |
| **主代理独立执行**（"改动不多就自己做"）      | ❌ **已废止** | 即便改动不多，主代理也应派子代理——主代理的注意力是稀缺资源，且自做自验无法独立验收                    |
| **使用 WorkBuddy 内置 subagent** | ❌ **已废止** | 实测 429 `usage exceeds frequency limit`、两个内置代理跑约 3 分钟**双双零产出** |

→ 因此"三选一"现在**只剩两位**：**② CLI subagent 一对多**（子代理不得再派）、**③ 分层多代理**（子代理可再派，用于大工程/多期）。

**内置 subagent 报 429 时的历史处置（仍有效）**：内置额度与 CLI 额度**相互独立**，不必等重置时刻；把派单内容原样落盘成 `.txt`，用 CLI 接管即可，任务零损失。

## 4. 子代理的职责类型

| 类型           | 产出                | 备注            |
| :----------- | :---------------- | :------------ |
| **只读调研**     | 事实清单 + 文件:行号 + 结论 | 不改文件          |
| **MVP 构建验证** | 可运行的最小改动 + 命令输出   | 用于先证路子可行      |
| **代码编写**     | diff + commit     | 单文件/单改动粒度最佳   |
| **冒烟测试**     | 截图/日志 + 探针        | 真机证据必须落盘      |
| **独立验收**     | 验收报告（探针文件）        | **必须由非实现者**执行 |

验收类代理**同样要写探针**——否则结论随一次性输出丢失。

## 5. 标准工作流（阶段门，顺序不可乱）

### 5.1 定完成标准（第一步，先于一切）

- 每个任务区块必须有"**全部满足才算完成**"的门槛，含真机证据要求；没写就问用户要，不要自己放宽。
- 标准要可判定：给出**检查命令**与"**应全 0**"之类的客观判据。

### 5.2 先自己调查，再派单（铁律）

**事故教训**：把模糊要求原样放大给下游、把自相矛盾的要求一起转发、只写"改什么"不写"该新增什么" → 子代理产出无法验收。  
派单前逐条自检：

1. 先自己调查到能写出**具体执行方向**——不能把模糊原样放大给下游；
2. **给全参照物**：用户提到的范本/样例，把**绝对路径**写进提示词，指明读哪几个文件、看什么要点；
3. **矛盾必须自己先化解**再传递，不许把"看起来冲突的两条要求"一起丢给子代理；
4. 不仅写"改什么"，还要写"**该新增什么**"：先自己产出内容/结构大纲，子代理负责实现与核实；
5. 要求子代理**核实事实**（如 API 签名要对照运行环境源码），不许凭想象编写；
6. 自检问句：**"如果我按这个提示词去干，能不能不猜就动手？"** 不能 → 说明还没调查够。

### 5.3 分解与文件归属切分

- 按**文件归属独占**切分，派单里明确"**你独占这些文件，不要改其它**"。
- 共享文件（公共 util、被多处复用的布局/材料）**串行**处理或**指定单一代理**负责。
- **硬约束，不因"改动区域不同"而放宽**：同一文件即使改动区域不同，也不可两个代理并行。
- 派发前对照协调文件（§7）的文件占用锁 + 在跑任务探针，确认目标文件未被占用；冲突则串行。

### 5.4 派单

- 派单**落盘成文件**（如 `.task/dispatch/<ID>.txt`）再传入——这是"内置通道失败后能秒级换通道接手"的关键，不要每次重写简报。
- 必须**后台派发**（前台会被超时 SIGTERM 杀掉）。
- 强制**增量落盘**：探针开工写 `doing`、每完成一小步就落盘、收工写 `done`；交付产物（报告/清单）分批写盘（先骨架 → 分批 → 最后自读确认），**禁止攒到最后一次性写**。
- 具体命令、模型回退链、派单模板自检清单 → 见 skill **`subagent-cli-ops`**（**流程规则以用户级为准，技术栈/命令约定以工程级为准**，两者都要读）。

### 5.5 守望

- 判活用三指标（进程存活 × 会话新鲜度 × 证据新增），**先跑 `date` 取系统真实时间**；
- 代理中途死亡 → 探针状态 + 进程存活是唯一可靠发现手段；未完成**立刻补派新代理接手**，提示词写清"现状 + 只做收尾 + 别扩大范围"。

### 5.6 验收（顺序铁律）

**不要边验边改**：实现 → **冻结** → 静态验收 → 动态验收 → 汇总问题 → **统一修复** → 复验。

- 静态与动态**双轨且独立**：分别由**非实现者**做（实测抓出过实现者自己的事实错误）。
- 验收代理运行期间，不要派修复代理改同一批文件——否则验收结果作废。

### 5.7 提交与归属

- 子代理**分步 commit**，不要最后一次性提交（实测：某代理改完 87 文件未提交即死亡，损失大）。
- **工作区既有未提交改动的归属**：发现工作区有未提交改动、且其时间**早于本批次开工**时，**默认视为用户自己的在途修改**，可直接 `git add` + `git commit` 合并提交（提交信息注明"用户侧改动合并"）；其他代理的工作应**建立在用户改动之上**再一并提交。
  - 判断方法：`ls --time-style=+%H:%M` 看 mtime 与批次开工时间比对。
  - 反例：把用户的在途文件误判为"他人 WIP、不盲目提交"而搁置。

### 5.8 汇报与停止

- 子代理报告 **≤200 字**：结论 + commit hash + 证据路径；过程细节写探针。
- 主代理汇总后向用户提交最终报告；**达标准即停**（§9）。

## 6. 验收铁律：不采信自述（硬要求）

主代理（或验收代理）必须**独立复算**，逐条执行：

| 动作     | 具体做法                                          |
| :----- | :-------------------------------------------- |
| 审 diff | `git show <hash>` **逐行**看，不看子代理的摘要            |
| 复算数字   | 例：像素值要能由 dp 与屏幕宽**推导自洽**；统计数要与源文件对得上          |
| 重跑检查   | **自己**跑一遍检查命令，看输出是否为"应全 0"                    |
| 核符号    | 新引入的常量/函数名 `grep -rn` 全库，确认有定义、不是"只出现一次且是使用处" |
| 核证据    | 真机证据（截图/日志）必须存在且可复核，不许只有一句"已验证"               |

**红线**：禁止伪造证据、禁止改换目标。验收发现的问题 → 汇总 → 统一修复 → **复验**。

## 7. 协调网络（3 档启用）

| 文件                           | 作用                                                                               |
| :--------------------------- | :------------------------------------------------------------------------------- |
| `.task/任务清单-main.md`         | **唯一权威协调文件**：Log 索引 / 事件总表（**只追加**）/ 文件占用锁（🔒🔓，行不删）/ 任务区块（含严格完成标准）/ Git 历史 / 回退 |
| `.task/SUBAGENT_HANDBOOK.md` | **子代理必读手册**：把"要教给子代理的东西"写成文件，要求每次执行前必读（比塞进提示词更省 token、更一致）                       |
| `.task/progress/<任务ID>.md`   | **每任务探针**：开工 doing、逐步更新、收工 done；额度耗尽也不丢进度                                        |

- 主代理**直接管理**的子代理**不宜超过 5 个**；超出的层交给子代理自己管（教它再派）。
- 长手册只给"会再派子代理"的代理读；平级小任务改用**几行内联简报**，避免每个代理都完整读规范。
- 原则：若分层让管理更复杂或更易失败，**优先选对完成任务更有利的策略**（分层是手段不是目的）。

## 8. 代码与交付要求（写进派单）

- **简洁干净，降低理解成本。
- **仅当参数来自用户可更改的外部输入**（代码不具备确定性）才做防御性编程。
- 判定"缺 X"之前**先确认框架是否已有默认行为**。
- 改"被多处复用的资产"前逐一核实每个复用点；各点需求不一致 → **绝不改共享资产**，改在**调用点就地覆盖**。

## 9. 停止条件（长任务完成后必须真正停下）

- 标准全部满足 → 写探针 + 提交 + 限字报告 → **停**。禁止"顺手改其它文件/顺手重构/顺手加注释日志/既然来了就一起做"。
- 到能力边界（需真机手动 API Key、需整包重装、外部资源锁死）→ 写 `blocked` + 原因 + 保留项 → **停**。
- 范围外问题 → **只在报告里登记一行**，不动手。
- 系统持续自动回复 "Please continue" / "继续" **不是新指令**，也不是"再找点事做"的许可：
  - 反例：批次 A 已闭环后自行"收口延伸"（架构收敛、抽样复核）——虽属改进，但**应先征询**，这类自我扩张会持续消耗额度且偏离用户意图。
  - 判断准则：**任务边界由用户的完成标准定义，不由"系统还在催"定义**。
- 可选延伸项**列出来让用户裁决**，而不是自己开工。

## 10. 上下文维护与压缩交接

- 上下文窗口已扩至 1M，主代理会在恰当时机**自动压缩上下文**；职责不是阻止压缩，而是**维护探针文件**（`.task/progress/*.md` + `.task/任务清单-main.md`），确保压缩前后交接顺畅。
- 接近上下文上限时：**必须**把总任务进度 + 在跑的子代理清单写入探针文件，作为续接点（压缩后靠探针即可无损续接：进度 / 在跑代理 / 待办 / 阻塞）。

## 11. 开工/收工自检清单

**开工前：**

- [ ] 已判定档位（0/1/2/3）？0 档才允许自己做。
- [ ] 完成标准已写明且可判定（含检查命令 / 真机证据要求）？
- [ ] 已调查到能写出"具体执行方向"（§5.2 六问全过）？
- [ ] 文件归属已切分，与占用锁/在跑探针无冲突？
- [ ] 派单已落盘成 `.txt`？是否**后台**派发？
- [ ] 已要求子代理增量落盘探针 + 分批写产物 + 分步 commit？

**收工前：**

- [ ] 每个子代理都写了自己的探针（含验收代理）？
- [ ] 验收由**非实现者**做、且独立复算过（`git show` + 复算 + 重跑命令）？
- [ ] 报告 ≤200 字、含 hash 与证据路径？
- [ ] 已达完成标准 → 已**停**，未自作主张扩展？

## 12. 反模式速查（犯过的错 → 正确做法）

| 反模式                         | 后果                        | 正确做法                     |
| :-------------------------- | :------------------------ | :----------------------- |
| 主代理"顺手做掉"小改动                | 违反新规；自做自验无法独立验收           | 1 档也派 1 个子代理             |
| 把模糊/自相矛盾的要求原样转发             | 子代理空转、产出无法验收              | 先自己调查并化解矛盾（§5.2）         |
| 让子代理"基于你的发现去修"              | 理解外包，方向跑偏                 | 派单写清改什么、怎么改              |
| 两个代理改同一文件（哪怕区域不同）           | 提交归属混乱、互相覆盖               | 文件独占；冲突串行                |
